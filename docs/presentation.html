DoubleRunner

A running-cadence companion for Rokid Glasses. It charts the stride from the head-mounted gyroscope, reads your cadence off that curve, and keeps a metronome at the cadence you are aiming for — all inside a 480 × 352 single-green display.

The screen

Six things, one glance

Everything a runner can act on while moving, and nothing else. The page never scrolls, never opens a menu, and never asks for a confirmation.

  1. 1Stride curve — the last 6 seconds of angular velocity on the dominant axis. Each detected step gets a dot and a tick along the top edge.
  2. 2Beat dot — lights for 110 ms on every beat, so the metronome is visible when you cannot hear it.
  3. 3Cadence now — 44 px figures, the one number you read at a glance. Median of the last 8 step intervals.
  4. 4Target and delta — 190 here, with +6 fast telling you which way to correct.
  5. 5Achieved beat rate — 3.2 beats per second, measured over the last 12 beats, not the rate that was requested.
  6. 6Steps — counted for this run only.
The line under the metrics always states where the signal comes from. Here it reads No sensor · showing demo signal, and the state chip carries · DEMO.

Three sizes, one green

One hue, five luminance steps

100%72%48%24%12%

#40ff5e only. Hierarchy comes from luminance, size, and position — never from a second hue, because the display has none. Structural lines stay at 1 px, controls take 4 px corners and panels 6 px, and no filled area goes above 12 % luminance so the optics stay readable against daylight.

Below 240 px of height the page drops the curve, the beat rate, and the step count, and keeps the state, the cadence, the target, and the hint. That is the inline card, and it is the same Page — one layout, two densities.
Using it

One button does the whole run

The temple click carries the run from start to finish. Nothing else is required while you are moving, and every transition is one gesture.

Leaving the page mid-run pauses it and releases the sensor; an unfinished run that has steps is saved silently on unload. The Back key is left to the host, so the glasses behave the way the rest of the system does.
Setting the target

Swipe the temple, the beat retunes

The target cadence is the one setting this app has, so it is bound to the gesture you can make without looking: swipe forward for +5, swipe back for −5.

Changing the target mid-run retunes the metronome on the next beat instead of restarting the sequence, so the rhythm never stutters while you are in step with it.

Voice reaches the same setting: “cadence 175” opens the page with targetCadence: 175. The agent is told to re-open the Page with the new number rather than answer in words.

The two traps it avoids

Double counting. One nod has two lobes. A step only counts once the signal has fallen back below the baseline since the last one — the detector has to re-arm.

Invented intervals. If samples stop arriving and resume later, the filters restart instead of treating the gap as one enormous stride.

The same detector runs on the accelerometer when the gyroscope is unavailable, with a 1.2 m/s² threshold; gravity is removed by the same high-pass.
The metronome

No buzzer, so the beat has to be heard and seen

The obvious design — buzz the temple at 180 spm — is not buildable on this platform. That finding shaped the whole feedback design.

What the runtime actually offers

Sound — local short sound effectavailable
AudioContext — synthesised toneabsent in 0.17
navigator.vibrate — hapticsdoes not exist
Vibration anywhere in the AIUI APInot documented

So the beat is a 1200 Hz, 35 ms tick with an 1800 Hz accent every fourth beat, plus the dot on the curve frame. The agent is explicitly instructed never to promise a haptic cue.

Consequence for the product: in a noisy street the beat is carried by the dot alone. That is a real limitation of the platform, not a choice, and it is worth re-testing the moment a haptic API appears.

Beats that cannot drift

// every beat is computed from the anchor, // never accumulated from the last callback dueAt = anchorAt + index * intervalMs; delay = max(0, round(dueAt - now()));

A late callback therefore shortens the next delay instead of pushing every following beat back. At 180 spm that is one beat every 333 ms, exactly 3 per second.

The host does not deliver timers reliably, so the beat is also polled from the frame loop and the UI refresh: as long as the page renders, the rhythm holds.
